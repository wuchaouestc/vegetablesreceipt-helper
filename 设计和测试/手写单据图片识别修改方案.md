# 手写单据图片识别修改方案

版本：优化稿 v3 · 2026-11-07

本轮仅更新文档，未修改识别代码、配置、词典或发布产物。优化前全文已归档备份。以下新增章节反映当前源码；后文保留为历史设计基线，其中“尚未实施”“待实现”和“首版默认原流程”等表述不代表当前实现状态。参数与验收目标不是效果承诺。

## 本轮核验结论与优化路线（2026-11-07）

### 1. 《手写单据识别方法》能否用于优化 handwriting

可以借鉴其“字符识别→空间关系→逻辑关系→语义分析”的思路，重点改善字段归属与错行，不能直接照搬数学公式计算算法。

已阅读方法文档及两张流程图片：第一张包含字符分割、字符识别、空间关系、逻辑关系、语义建立及表达式计算，并列出端到端识别路径；第二张展示灰度/二值化、CNN 字符分类、字符分割、结构/文法分析和后缀计算树。迁移到单据时，应将运算树替换为可追溯的字段证据关系。

| 原方法 | 单据中的对应设计 | 当前基础与限制 |
| --- | --- | --- |
| 字符分割和分类 | OCR 文字块及字词、数字候选 | 复用现有 OCR/模型，不先新建字符 CNN；连笔和小数点不宜强制逐字切分 |
| 空间关系 | 页→栏→行→标题→明细→字段 | `geometry.py` 已有完整框、分栏、行聚类和标题关联，需验证复杂版式 |
| 文法分析 | 编码、数量、单位的局部语法 | `ENTRY_RE` 主要识别“编码:数量单位”，无冒号、缺单位等写法需要专项扩展 |
| 语义分析 | 品类词典、编码候选、单位含义及备注从属 | 词典仅提供候选；不能假设编码唯一决定品类或数量 |
| 后缀计算树 | 行和字段节点、来源框、标题从属及冲突关系 | 保留来源与候选，总计只辅助校验，不凑总数改数量 |
| 最大化预测概率 | 依据图像与同行证据排序候选，允许无法裁决 | 当前是规则证据链，规则分数不能冒充整行正确概率 |

方法文档未提供完整算法、训练集和可复现评测。“MyScript 表达式正确识别 67.65%”缺少来源与评测口径，不能作为本项目单据准确率或收益依据。灰度、二值化可能损伤淡笔画和小数点，仍遵守第六节暂不实施图片增强的范围。

建议流程：原图 OCR/模型候选→完整框和原文→分栏、行与标题关联→五字段证据及词典候选→冲突局部复核→人工确认。先利用现有模块补齐结构关系，不把数学计算模块移植为业务推断器。

### 2. 字典当前对五个字段的实际作用

**handwriting 有词典能力，主辅助通道也使用词典候选，但主要帮助校验和人工核对，不能据此宣称底层识别准确率已提高。**

依据：`vocabulary.py` 的加载、候选和注释 API；`pipeline.py` 的实验与辅助通道；`evidence.py::build_evidence`。

| 字段 | 已实现 | 尚缺能力及边界 |
| --- | --- | --- |
| 品类 category | 规范名/别名的精确及字面包含匹配；辅助通道保存候选和词典外提示 | 不是通用形近字检索；不因词典外而删除新品类，不跨标题强制改类 |
| 编码 customer_code | 规范值/登记别名精确匹配，按字符串保存 | 不做最近编码自动替换，保留前导零；编码不是商品身份的默认唯一依据 |
| 斤数 weight | 不属于词典字段；依赖同行 OCR、模型冲突及区域复核 | 不建立常见斤数替换表；拟增加格式、小数点、精度和经确认的范围校验，异常只提示 |
| 单位 unit | 词典候选；几何解析器另有固定单位正则表 | 两套机制尚未统一；当前两路单位冲突只记 observations，不单独触发疑点；输出规整会把空单位回填“斤”，需单独评估 |
| 备注 remark | 词典格式、实验通道结果注释和人工学习支持 | 主辅助通道未把备注加入词典候选循环、主要证据裁决及局部复核回填，五字段支持尚未完整贯通 |

`build_prompt_context()` 已定义，但当前流水线及主界面手写补丁未调用它，模型接收的仍是原有 `request.prompt`。辅助通道在基础模型返回后加载词典生成证据，词典建议本身不会自动覆盖识别字段。因此应区分“识别后提供建议”与“模型识别时使用字典”。

文件存在不代表词典正在生效：`modes.py` 的默认“手写词典辅助”为空，应核对实际配置路径、revision、客户范围及命中数量。主界面 `_手写识别` 未传入 `RecognitionRequest.customer`，有客户 scope 的条目可能无法命中，后续需补齐客户上下文并验证隔离行为。当前模式已支持自动判别，不能继续按历史规划认为默认一定走原流程。

### 3. 人工学习与词典治理

`learning.py` 已提供人工确认结果、别名及示例保存能力，数量明确不进词典。这是数据积累及候选提示，不是自动训练识别模型。当前 `learn_vocabulary()` 可将一次纠错收录为启用别名，尚无待审核和多次独立确认门槛。

本次检查的 `data/dictionaries/handwriting.json` 存在启用的“个→斤”别名；一次纠错不能证明两种单位等价。当前仅为候选，仍可能误导人工；未来接入模型提示前应先审核，不能直接把单次错读升级成全局规则。本轮不修改现有词典。

建议分开管理：经审核的规范词及真正等价别名、带图片/字迹/客户范围的误识别候选、逐次人工确认记录。新纠错先进入待审核区；单位跨语义纠错和编码错读不得直接成为全局替换。保留来源、范围、版本、停用及撤销，迁移前备份用户词典。

主界面打印包装在 `_原_do_print()` 返回后调用学习；该返回不证明后台打印成功，前置检查提前返回也可能继续学习。后续应以真实人工确认状态作为学习依据，将打印完成状态独立记录，不能把源码注释“打印成功后”当作成功证据。

### 4. 后续实施与验证顺序

1. 先补词典可观测性和审核：记录实际路径、版本、客户、候选数量、禁用原因，核查加载警告是否到达界面；审核危险别名，不自动改变当前开关。
2. 补齐五字段证据：备注保留开放文本及本行/跨行来源框；单位显示冲突和缺失来源；数量保留原文与小数点。单位兜底策略另做打印兼容验证，避免与词典提示一起改。
3. 小范围接入模型候选：在模型调用前从 OCR 观察生成有限的已审核候选，图片优先、允许新值；候选指纹纳入缓存键。当前精确/包含匹配可能找不到完全错读的词，不能靠发送全库弥补。
4. 加强结构关系：分别覆盖无冒号、缺单位、同编码重复行、跨栏同高度、跨行备注和标题边界。定位失败保留原始明细与疑点，不能静默删行。
5. 固定输入、客户、配置、模型、服务、预算及缓存口径做对照：A 当前辅助通道；B 仅审核词典并补客户上下文；C 仅增加模型候选；D 仅加强结构；E 组合已验证有效的项。保留独立人工确认的冻结验收集，不能把答案用于提示。

分别统计品类、编码、斤数、单位、备注准确率，以及漏行、重复行、错行、未提示错误、人工时间和请求成本。备注的空值与文字差异口径预先固定；不以待核对数量减少证明准确率提高。补充未知词、新单位、前导零、小数、客户隔离、词典损坏、关闭辅助及正常印刷路径回归，发布前验证实际产物。

本轮仅完成文档和源码静态核对，未重新调用识别接口或打印，未产生新的准确率结论。以下原方案继续作为设计基线，后续开发以上述已实现/待补齐清单为准。

## 一、目标与范围

打单助手面向蔬菜、生鲜农产品批发，将拍照、截图或手写单据转换为明细并打印标签。本次拟增加独立的手写识别功能库，保留原稿的四条主线：

1. 温和增强图片，处理偏暗、阴影、倾斜和背景干扰。
2. 对照验证识别引擎，降低手写字和数字误读。
3. 对疑难区域裁剪复核，重点保护小数点、相似数字和单位。
4. 利用业务词典、空间位置和校验规则，减少品类、编码与数量错配。

优先降低“错误结果被当作正确结果”的风险，其次减少漏行、重复行和人工核对负担，再平衡耗时及费用。不能以识别条数增加、待核对条数下降或图片看起来更清晰，单独证明正确率提升。

本次不改客户打印过滤、标签格式和单位换算规则；不自动收紧品类或编码白名单；不覆盖原始图片。印刷单保留既有通道，手写功能可单独关闭。

## 二、当前实现与核验前提

以下来自本项目当前源码检查，不代表外部接口实测结论：

| 当前实现 | 对新方案的影响 |
| --- | --- |
| `ttsb2.py::recognize_parallel()` 并行调用腾讯 OCR 和模型，仔细模式增加一遍模型请求 | 新增复核需要统一调用预算，不能无限叠加识别次数 |
| 腾讯调用 `GeneralAccurateOCR`；腾讯和模型均读取输入原图 | 尚无统一的识别前画质增强入口 |
| `compress_image()` 可以缩小长边并转换 PNG，但当前没有调用 | 不直接启用固定 1400 像素缩图，先检验细字和小数点损失 |
| `_ppstructure/grid.py` 有方向校正、灰度化、缩放、二值化 | 用于表格线检测，没有把处理图送给主 OCR/模型 |
| OCR 结果目前只保留文字及多边形首点 `x/y` | 裁剪与同行证据需要完整文字框，不能只靠左上角猜边界 |
| `_record_ocr_support()` 在全页文字中寻找品类、编码和数字 | 各字段分别出现不等于来自同一行，需要区域关联 |
| 已有共识合并、合计裁决和 `fix_category_boundaries()` | 新旧裁决要明确边界，避免旧逻辑提前消除疑点 |
| 主界面调用 `build_prompt(None)`；另有 `is_handwritten()` 辅助函数 | 不能认为客户标记已自动驱动当前手写流程，需要显式接入文档类型 |
| 结构补丁包装 `extract_once()`，正常并行通道直接调用 `deepseek_parse()` | 不能认为开启“结构增强”后每次模型请求都有结构卡，须核验实际注入 |
| OCR 缓存主要按图片哈希区分 | 新接口、参数和增强版本不能混用旧缓存 |

### 外部接口事实

- 腾讯官方目前将 `GeneralHandwritingOCR` 标为旧版本，并推荐使用高精度通用识别。软件正在使用的高精度接口应保留为基线；旧手写接口只在账户支持且有对照价值时试验，不能因名称含“手写”就默认替换。[腾讯官方文档](https://cloud.tencent.cn/document/api/866/36212)
- 当前代码使用 `deepseek-chat` / `deepseek-reasoner`；本次查阅的视觉文档列出 `deepseek-flash`。实施前核验实际账户、模型、图片输入能力、响应和费用，不能根据函数名认定现有图片通道正常，也不未经对照直接更换模型。[DeepSeek 视觉文档](https://api-docs.deepseek.com/guides/vision/)
- PaddleOCR 提供文档方向分类和几何畸变校正能力，可作为后续候选；本机依赖是否支持、是否改善手写单据，需独立验证。[PaddleOCR 文档预处理](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/doc_preprocessor.html)

## 三、校对库拆成业务词典与人工校对集

原稿提出的“单据结果校对库”分成两类，避免把提示候选当成标准答案。

### 3.1 业务词典：提供候选，不封闭真实业务

| 字段 | 建议约束 | 不允许的处理 |
| --- | --- | --- |
| 状态 | 由软件生成待核对、已确认等状态，与打印状态分开 | 要求模型把图片文字识别成程序状态 |
| 品类 | 标准名、已确认别名、适用范围、来源及启停状态 | 因不在词典中就删除新品类；合并相近但不同的商品 |
| 编码 | 按字符串保存；保留字母、前导零；提供常见编码候选 | 用最近的合法编码强制替换；删掉前导零 |
| 数量（界面原称斤数） | 十进制数值与原文并存；已确认的范围和精度用于提示 | 枚举成固定数量列表；用常见数量补猜不清的数字 |
| 单位 | 常见单位、明确的等价写法；未知单位保留待核对 | 默认把“个、把、袋”等改成“斤”；无依据换算 |
| 备注 | 开放文本，常见加工描述只作提示 | 强制限制为枚举，丢掉新备注 |

词典文件具有 `schema_version`、`revision`；词条具有 `id`、`canonical`、`aliases`、`scope`、`source`、`confirmed_at`、`enabled`。数量规则单独保存，不混入词汇枚举。实际别名和数值限制必须经业务确认，不从猜测生成。

使用规则：

1. 模型只接收与本图有关的有限候选，并明确“图片优先，候选不完整，允许新值，看不清则保留疑点”。不发送全库或无关客户资料。
2. 客户范围可以帮助生成候选，但不能成为删行、改数量或排除编码的依据；词典外记录仍保留。
3. 原始识别字段与规范化字段分别保存。只有确认无歧义的等价写法可直接规范化。
4. 形近字、相近编码和多义别名仅产生建议。自动修正需有同一区域图像/OCR 证据，并保存前后值、来源和原因。
5. 人工修改可加入待收录列表，但不能一次修改就成为全局替换规则；避免错误反馈污染词典。
6. 词典缺失、损坏或版本不兼容时禁用词典辅助并提示，保留识别功能。写入前备份，使用临时文件与原子替换。

### 3.2 人工校对集：用于评价，不发送给模型

当前递归检查 `data/手写素材` 发现 13 个图片文件（12 JPG、1 PNG），另有 `data/手写.zip`。尚未逐张审核、去重和标注，不能直接称为 13 张独立合格测试单据。

每图标注：图片哈希、来源分组、困难类型、文档类型、区域框，以及每条明细的品类、编码、数量、单位、备注。重复明细按位置分别保留；划掉、改写、补写内容要注明处理依据。不能辨认的内容标为“待人工裁定”，不编造标准值。

划分调试集和冻结验收集。同一单据的原图、截图、裁剪和增强副本归入同一组，避免泄漏。验收答案不加入提示词，也不用于临时建立只针对验收答案的词典。

先用现有素材验证流程，再逐步补足约 30～50 张不同字迹、光照、密度和版式的单据。此数量只是起步建议，不保证统计充分；样本不足时只报告试验结果。

#### 单据图片识别后，在软件的界面上面是可以人工核对，当用户完成数据核对纠错后，要做一个标注数据文件保存到“data”文件，让软件越用越智能。
    

## 四、模块、目录与数据契约

建议结构如下，均为待实现设计，不表示这些文件已经创建：

```text
handwriting/                 # 独立、可测试的手写识别包
  pipeline.py                # 编排、任务上下文、预算和降级
  preprocess.py              # 图片副本、质量检查、坐标变换
  providers.py               # OCR/模型适配和响应标准化
  vocabulary.py              # 词典、提示候选和规范化
  evidence.py                # 行列关联、证据和冲突
  review.py                  # 区域裁剪及复核
data/                       # 位于程序目录
  dictionaries/              # 用户业务词典、规则和版本
  手写素材/                   # 原始测试素材，仅开发评测使用
  annotations/               # 人工标准答案，仅评测使用
  evaluations/               # 输入清单、对照结果和报告
  handwriting_cache/         # 分版本缓存、增强副本和复核区域
```

数据根统一使用 `路径.程序目录() / 'data'`。源码和发布版各自对应程序目录，不能根据当前工作目录或 `_internal` 推导用户数据位置。

新包不直接依赖 Tk 控件，建议内部契约：

| 对象 | 必需信息 |
| --- | --- |
| `RecognitionRequest` | 任务 ID、图片路径/哈希、文档类型、配置快照、词典版本、预算、取消标志 |
| `ImageVariant` | 原图哈希、变体 ID、实际尺寸/格式、处理参数、原图坐标变换及逆变换 |
| `OCRBlock` | 文字、完整多边形、原图坐标、接口来源、变体 ID、可选置信信息 |
| `RecognitionResult` | 完整明细、字段原文、候选、区域引用、核对原因、调用来源、错误和耗时 |

适配层维持现有 `(records, blocks, notes)` 返回约定，保留 `_id`、`_img`、`_src` 等字段；额外证据单独关联，避免重写打印流程。第三方未提供置信度时保留未知，不编造概率。

## 五、启用方式与总体流程

第一版建议每张图片可选择“原流程 / 手写辅助”，批量可统一选择。客户档案只提供文档类型建议，用户可覆盖；混合单不能仅按客户一刀切。第一版不开发自动分类模型。

```text
读取原图、配置和词典版本快照
  → 原流程：进入现有识别
  → 手写辅助：质量检查，必要时生成一个轻度增强副本
      → 基础 OCR 与模型识别
      → 同区域行列关联、词典辅助校验
      → 有疑点且预算允许：原图局部裁剪复核
      → 合并候选，保留未解决疑点
      → 界面人工核对，沿用既有打印流程
```

“仔细模式”控制额外核验力度，“手写辅助”控制手写预处理和证据策略。一起开启时由统一预算约束，不能每条分支再各自重复重试。

试验阶段保留原图请求作为对照。正式路径默认使用原图还是增强图，由验收决定。建议初始限制为每图最多一个增强变体、两个复核区域，每区一个追加识别请求；相邻疑点合并区域。超时重试也计入预算；总请求数、费用、总时限任一超限即停止追加并转人工核对。具体预算在基线测量后确认。

## 六、温和图片增强  （暂不实现，现在手写单据图片质量还可以。）

| 处理 | 启用条件 | 验证与回退 |
| --- | --- | --- |
| EXIF 方向归一化 | 照片带方向信息 | 保留原文件，显示和识别坐标一致 |
| 背景裁剪 | 可靠找到完整纸面或内容区域 | 留边缘余量；边缘有字或边界不确定时跳过 |
| 亮度与局部对比度 | 偏暗、对比不足 | 保护淡笔画、小数点和高亮区域，不一律拉白 |
| 阴影校正 | 明显不均匀光照 | 生成候选副本，避免把淡字当背景去除 |
| 小角度纠偏 | 有可靠方向证据 | 竖排、多栏可能干扰估计，不可靠时跳过 |
| 透视/曲面矫正 | 倾斜或弯曲明显且定位可靠 | 后续独立试验，不纳入首版默认处理 |

不默认强锐化、强去噪、强二值化、去表格线或生成式笔迹修复；不宣称放大能恢复丢失信息。严重模糊、反光遮挡时提示重拍或人工核对。

每个变体保存参数、尺寸和坐标映射。OCR、模型、结构卡使用不同变体时，统一映射到原图坐标；不能混用缩放后的 OCR 点与原图像素。保留真实 MIME 类型，不将所有图片一律声明为 PNG。

优先复用 Pillow。需要新增 OpenCV 或 Paddle 模型时，独立记录依赖、包体、内存及启动耗时，验证后再发布。

## 七、接口对照、缓存和故障处理

### 7.1 接口对照

- 保留当前 `GeneralAccurateOCR` 为基线；旧手写接口可用且有试验价值时才比较。
- 不默认使用“只输出手写体”参数，以免混合单的印刷表头被过滤。
- 固定图片、模型、提示词和配置，每次只改变增强、词典或 OCR 接口中的一项。
- 接口返回成功、返回了文字、提取到正确明细是不同层次，分别记录。
- 如需换模型，另建新基线，不把模型变化归因于图片增强。

### 7.2 缓存

- OCR 缓存键包括原图/变体哈希、接口、请求参数、预处理版本和响应格式版本。
- 模型及复核缓存另含模型、提示词哈希、相关词典版本、输入 OCR 指纹、裁剪区域及复核策略版本。
- 原图、增强图、不同引擎和词典版本隔离缓存；耗时区分冷缓存、热缓存。
- 网络或鉴权错误不能缓存成“成功但零文字”；无文字、接口失败、返回格式错误分别表示。
- 缓存定期清理有独立容量/保留策略，不删除原图、词典和人工标注；默认不把缓存带入发布包。

### 7.3 降级

增强、词典、服务或复核失败时，返回明确原因和已有证据。只有恢复完整旧流程时称为“回退原流程”；仅剩某一路结果时称为“降级结果，待核对”，不伪装成原流程成功。降级重试仍受总预算限制。

日志记录任务 ID、图片哈希、版本、来源、请求 ID、耗时和原因；不写密钥或完整 Base64。详细识别证据默认保存在本地，词典仅发送必要候选。

## 八、疑难区域、行列关联和裁决规则

触发复核的情况：关键字段冲突、小数点疑似缺失、模型自报模糊、缺少同行证据、疑似漏行或重复行。词典外值只触发核对，不直接判错；合计异常必须基于真实合计及同一单位。

裁剪原图时保留上下相邻行、所属品类标题、编码、数量和单位。跨栏单据先确定栏，再确定行，不能全页按 y 坐标简单聚行。无法可靠定位时转人工，不猜区域反复识别。

裁决规则：

1. 编码、数量、品类必须属于同一明细位置或明确的标题从属关系。数字在全页出现不能确认本行数量。
2. 同一模型两次一致只是一致性证据，词典约束下的一致也可能共同出错；不据此清除已有冲突或自报模糊。
3. 合计用来发现异常和辅助核对，不能仅凭凑合计修改数量、移动品类边界；无合计单据不构造合计。
4. 同品类、同编码的重复出现可能是两条真实记录。用原图位置或稳定 ID 区分，不能按值去重。
5. 划掉、改写、增补分别保存证据；无法确定哪一笔生效时标记核对，不静默删行。
6. 局部复核不得覆盖已确认或手动修改的结果；晚到响应须校验任务 ID、图片版本和行版本。

现有合计裁决和品类边界修正与上述规则存在差异。实施时对手写辅助通道增加门控，保存裁决前候选，避免旧逻辑先消除疑点；原流程保持可回退。此项单独对照评估，不混入图片增强试验。

## 九、界面和线程约束

- 提供模式选择；设置页提供增强、词典辅助、局部复核开关，首次升级默认仍走原流程。
- 显示具体原因，如“数量两路不一致”“缺少同行证据”“词典外品类”，避免只有笼统低置信度。
- 点击核对项查看原图区域、原文、候选和建议；可切换增强图，但原图始终可见。
- 保留原有确认打印流程；本轮不擅自改变“待核对能否打印”，需要调整门槛时另行确认。
- 主线程启动前读取 Tk 状态，生成不可变快照；后台只处理数据，通过队列更新界面。
- 成功、失败、取消和降级都发送结束消息并释放 busy；取消后忽略晚到结果，防止覆盖新任务。
- 回归覆盖 release/debug、日志展开/收起，确保日志异常不阻断结果和错误回调。

## 十、实验和验收

### 10.1 对照分组

| 组别 | 相对基线的变化 | 目的 |
| --- | --- | --- |
| A | 无，当前原流程 | 保存固定基线 |
| B | 只增加温和增强 | 判断画质处理收益与退化 |
| C | 只增加词典候选及校验 | 检查帮助与强改新值风险 |
| D | 只换候选 OCR，满足可用前提 | 判断引擎差异 |
| E | 增加区域证据、局部复核和保守裁决 | 判断错行及未提示错误改善 |
| F | 组合已经证明有效的项 | 检查组合效果及相互影响 |

E 组先分别验证区域证据和局部复核，再合并测量，避免无法归因。每组固定图片哈希、客户/文档类型、依赖、配置、服务状态、模型、提示词和缓存策略。词典实验仅改变必要词典上下文，其余提示词不动。

对随机模型可重复三次，报告每次结果及波动，不能挑最好一次。标注与输出的匹配规则预先固定，按原图位置一对一关联；不因数量相同就跨行匹配。

### 10.2 指标

| 指标 | 定义 |
| --- | --- |
| 明细召回率 | 匹配到的真实明细数 / 标注明细数；重复明细按位置分别计数 |
| 明细精确率 | 匹配到的真实明细数 / 输出明细数；虚构和重复输出记错 |
| 关键字段准确率 | 在已匹配明细上分别计算品类、编码、数量、单位正确率 |
| 整行完全正确率 | 所有关键字段正确的明细数 / 标注明细数 |
| 未提示错误 | 实际有错但未标为待核对的明细数，并报告占全部输出的比例 |
| 核对负担 | 待核对比例、错误被提示比例、正确行误提示比例、人工处理时间 |
| 性能成本 | 每图耗时中位数/P95、请求数、费用估算、失败及降级比例 |

报告按清晰、阴影、倾斜、密集、涂改等类别拆分；小样本不夸大 P95 或统计显著性。提示全部记录为待核对虽然可降低未提示错误，也不能被视为完整成功。

### 10.3 建议发布门槛

以下需在基线建立后确认，不是效果承诺：

1. 冻结集关键字段错误减少，初始可用“相对下降至少 20%”作为试验目标；错误基数过少时逐例报告，基线为零时不计算相对改善。
2. 不新增未提示的关键字段错误；明细召回和精确率不下降。清晰手写与困难手写分别验收，不用平均值掩盖退化。
3. 关闭新功能后，本地固定输入处理回到原逻辑；非手写路径、客户过滤和打印字段通过回归。云端随机结果不要求逐字一致。
4. 实现前确定额外等待和费用上限；即使准确率改善，超限也不发布为默认模式。
5. 少量素材上的改善不能证明普遍有效；扩大验证前保留人工核对，不默认全量开启。

必测场景：浅小数点、字母编码及前导零、新品类、新单位、同编码重复行、跨栏、划掉改写、空白图、EXIF 旋转、边缘文字、词典损坏、缓存变更、接口超时、取消与晚到结果、日志开关和真实发布 EXE。

## 十一、分阶段交付

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| 0：基线 | 去重标注、接口能力核验、原流程报告、时间费用预算 | 可复现现状，明确主要错误来源 |
| 1：词典基础 | 格式、加载校验、只提示不强改、候选预览 | 不丢未知值，不改过滤，故障可降级 |
| 2：单项试验 | 增强、OCR 独立对照报告 | 分别有收益并记录失败样例，无收益项不接入 |
| 3：证据和复核 | 完整框、行列关联、候选追踪、统一预算 | 关键错误下降，不能裁决则保留疑点 |
| 4：组合与界面 | 模式切换、原图对照、冻结验收报告 | 满足质量成本门槛，旧流程回归通过 |
| 5：发布 | 暂存构建、实际 EXE 验证、数据保护及回退说明 | 发布环境验证通过后用于日常业务 |

首版优先支持现有多栏手写单，采用手动模式、词典候选及可选轻度增强。自动分类、强透视校正、自学习词典、多引擎全量投票不作为首版必需项。

## 十二、发布与回退

修改前备份代码、配置、词典和发布产物。修改 `build.py` 时将用户 `data` 纳入保护；默认词典仅在缺失时安装，升级按条目和版本迁移，不覆盖用户修改。测试素材、标准答案、评测报告及缓存不随正式程序默认打包。

新设置只补缺失键并保留已有值；识别期间设置变化只对新任务生效。验证实际 EXE 的模式切换、词典路径、缓存、识别结束回调和标签预览，不能以启动自检代替业务验证。

回退分两层：关闭手写辅助恢复原通道；若程序升级有问题，恢复备份产物并核对配置和数据兼容。新旧缓存隔离，不删除用户数据，不强制关闭正在处理单据的窗口。

## 十三、实施前待确认

1. 品类别名及常见编码有没有已确认资料；没有时先用空词典或少量人工确认样例，不自动猜规则。
2. 人工标准答案由谁复核，哪些单据留作冻结验收集。
3. 每张单据可接受的额外等待及费用预算。
4. 是否采用首版手动选择“手写辅助”，默认继续原流程。

这些事项不阻碍先整理标注模板和现状报告，但正式开发、付费接口试验及默认策略变更，应在后续实施任务中明确范围。本轮只完善方案文档。
