## 一、这次要解决什么

1. 用目标图实测独立手写识别库，确认真实接口下能不能跑通；
2. 给业务人员一个**网页**来核对 AI 读出来的数据；
3. 核对完成后**自动落一份标注数据文件到 `data/`**；
4. 让软件**越用越智能**：每次人工纠错都变成下次的识别依据。

## 二、实测暴露的真问题：模型返回的是分组结构

第一次拿目标图跑 `assisted_recognize()`，结果是这样的：

```
=== 明细 6 条 ===
  [00] None  None  None  None | 缺少同行证据：原图这一行没找到可对应的文字
  [01] None  None  None  None | 缺少同行证据：原图这一行没找到可对应的文字
  ...共 6 条全是 None
```

模型返回的原始结构不是逐行明细，而是**按标题分组**：

```json
{"records": [{"name": "马家柚", "entries": ["1368: 10个", "27: 24个"]},
             {"name": "古城千禧", "entries": ["933: 2个(大)", "931: 10个(小)"]}]}
```

而证据链（`evidence.build_evidence`）按**逐行扁平结构**消费明细——
`record['customer_code']`、`record['weight']`、`record['unit']` 全都取不到值，
于是每行都落成「缺少同行证据」，**整条裁决链直接失效**：
品类无从配对、数量无从比较、单位无从核对。

这不是模型出错，是**库对模型返回结构过于乐观**。手写单据本来就是
「一堆品类标题，每个标题下若干条明细」，模型这么返回是完全合理的。

### 修法：`handwriting/model_records.py`

新增归一化模块，只做**结构转换，不改数值**：

| 处理 | 说明 |
| --- | --- |
| 分组展开 | `{"name": 标题, "entries": [...]}` → 若干条扁平明细，标题带进该组每条的 `category` |
| 明细文字解析 | `1368: 10个`、`935: 1.5个(大)` → 编码 / 数量 / 单位 / 备注 |
| 区间写法 | `1-2个` 原样保留并标 `_ambiguous='range'`，**不擅自取其一** |
| 读不出的编码 | 留空 + 记一条提示，**绝不猜** |
| 区间括号备注 | `(大)` `(小)` 提取到 `remark` |

归一化后同一张图变成：

```
=== 明细 11 条 ===
  [00] 马兄弟的    1368  10  个 | 品类两路不一致（两路都读不准），需人工核对标题
  [02] 老赵干苦力   933   2  个 | 品类两路不一致…；局部复核与原图行内文字一致，编码已采信
  [09] 力虫蒜      15   25  个 | 品类两路不一致，已按原图标题文字修正
  ...
=== 复核区域 === 2
```

**6 条空洞 → 11 行有证据的明细**，并自动规划出 2 个局部复核区域。

顺带修掉的两个问题：

- `Entry` 是 frozen dataclass，词典别名不能 `append`，改用 `dataclasses.replace` 重建；
- 归一化往明细里塞内部键会破坏「原样返回模型明细」的约定——
  内部键已全部去掉（位置由下标得到，标题读数已由 `category` 承载），
  原记录上的其它键（如 `_id`）必须保留。

## 三、核对网页

`handwriting/review_web.py` + `handwriting/review_page.html`，
只监听 `127.0.0.1`，不对外暴露。

| 路由 | 作用 |
| --- | --- |
| `GET /` | 核对页 |
| `GET /api/payload` | 核对数据（每行的 AI 读数、当前值、候选、原因、原图坐标、类似示例） |
| `GET /api/image` | 原图 |
| `GET /api/crop?row=` | 该行在原图上的裁剪图（按原图坐标裁，保留上下文） |
| `POST /api/confirm` | 提交核对结果 → 落标注 + 学习 |

页面能力：

- 左边原图，右边逐行卡片，**不用来回翻图**；
- 每个字段下方列出**各来源候选**（模型 / 原图行内文字 / 原图标题 / 词典 / 局部复核），
  点一下就填进去，不用手打；
- 每行显示**具体核对原因**（「品类两路不一致（两路都读不准），需人工核对标题」），
  以及原图标题与行内文字；
- 原图上**没对上任何明细的文字**单独列出，可以一键「补成一条明细」——
  这直接解决模型说的「原图有 N 处文字没对上任何明细，可能是漏行」；
- 可删掉误识别的行，可手工补充漏掉的行；
- 缺复核人、缺关键字段时**拒绝保存**并指出是哪一行哪个字段。

### 启动

```powershell
# 用已保存的识别结果（不联网）
.\.venv\Scripts\python.exe -m handwriting review "data/手写素材/0a07371a8f56afba76dcb5de02f9b015.jpg" --records "data/evaluations/目标图实测/records.json"

# 或者现场重新跑真实接口
.\.venv\Scripts\python.exe ".setup/核对网页_目标图.py" --live
```

## 四、越用越智能：三份产物

一次人工核对产出三样东西（`handwriting/learning.py`）：

| 产物 | 位置 | 作用 |
| --- | --- | --- |
| **标注文件** | `data/annotations/<image_sha256>.json` | `review_status=confirmed`、`complete=true`，与 `dataset.prepare` 同 schema，可直接进 `annotation_audit` 和冻结评测 |
| **词典别名** | `data/dictionaries/handwriting.json` | 「AI 读错的写法」→「人工确认的规范值」 |
| **已确认示例** | `data/learning/confirmed_examples.json` | 人工确认过的明细 + 原图坐标 + 纠错前后对照，核对时直接参考 |

### 学的到底是什么

拿本次实测举例，模型把标题读成了「马兄弟的」「沙美」。人工确认真值是
「马蹄肉」「沙姜」，于是词典里长出两条别名：

```
category：马兄弟的 → 马蹄肉
category：沙美     → 沙姜
```

**下一次识别再读到「马兄弟的」，词典就能提示「马蹄肉」**——
不用人再去翻原图对照。这是「越用越智能」最直接的一环。

### 铁律（与阶段 3 的保守裁决一致，不可违反）

1. **只从人工确认的数据学习**，草稿和未完成的一律不学；
2. 学到的东西**只作提示，不静默改值**——裁决权仍在原图证据链手里；
3. **数量不进词典**：数量是数不是词，把「10斤」记成别名会污染语境；
4. 每条别名都能追溯到来源图片、行号与复核人；
5. 缺关键字段时**拒绝保存**，不写半成品标注；
6. 写盘前先校验，失败不动原文件（`save_vocabulary` 自带备份 + 原子替换）。

### 一处顺带修正

原实现里「词典外品类 / 词典外编码」在**词典为空时也会标**，
导致每行都被打上疑点——那是噪声不是提示。
现在改成：**词典为空不标；词典有内容后，「词典外」才真正代表「这个值没人确认过」**。

## 八、边界与限制

1. **这次只跑了 1 张图**。目标图是多栏疏排手写单据（左缘被裁断），
   模型把标题读成了「马兄弟的」「老赵干苦力」「力虫蒜」「小蓝美」这类，
   说明**草写标题仍然是最大错误源**，人工核对不可省。
2. 归一化只做结构转换，**不解决模型读错字**。「沙美 vs 沙姜」这种，
   只能靠原图标题的置信度裁决，或者人工确认后进词典。
3. 局部复核仍只解决「第三路跟哪一路一致」；两路都不一致时保留疑点。
4. 词典**只提示不强改**：它提高的是核对效率（少打字、少翻图），
   不直接提高自动裁决的正确率。
5. `data/annotations/` 里目标图原有一份 `draft_visual` 草稿（AI 目测，0 条记录）。
   人工确认后会**另写** `confirmed` 文件，不覆盖草稿。
6. 阶段 5（暂存构建、实际 EXE 验证、数据保护与回退说明）仍未做。
