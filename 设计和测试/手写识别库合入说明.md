# 手写识别库合入主流程 —— 开发与验收说明

日期：2026-11-06
需求：独立手写识别功能库已完成，**合入软件**；识别到手写单据图片时自动走手写库，获得更好的识别结果。

---

## 一、合入前的问题

阶段 3/4 的手写识别库已经建好，但接在界面补丁里，**要人去界面上下拉框手动切到「手写辅助」才会生效**，
默认是「关」。这跟需求「当识别图片是手写单据图片，则使用这个手写识别功能库」差着一层：
用户不该为了拿到更好的结果，先去判断哪张是手写的、再去点一下。

合入要解决的是**自动分流**：软件自己认出这是手写单据，然后自动走手写库。

难点在「怎么认出这是手写单据」。

---

## 二、判据设计：为什么不能用客户档案

第一反应是查客户档案。现网 `customers.json` 里 7 家客户只有「农和」标了 `doc_type: handwritten`，
其余 6 家都是 `printed`。按档案分流看起来够用——**但它是错的**。

实测导入目录：13 张手写素材分散在 **6 个不同日期**下，同一个客户会同时送来印刷单和手写单。
按档案分流会把某个客户送来的手写单判成印刷单，恰恰丢掉最大的收益来源。

所以判据必须落在**图像本身**。

---

## 三、判据实验：第一版方向反了

### 3.1 第一版：表格线检测（已废弃）

思路很自然：印刷单据是 Excel 导出的，有贯穿整页的表格线；手写单据是白纸。
用 PIL 逐像素扫「长横线/长竖线占比」来区分。

**实测下来结果是反的**：

| 类别 | 横线行占比（中位） | 竖线列占比（中位） |
| --- | --- | --- |
| 手写（13 张） | 0.968 | 0.976 |
| 印刷（102 张） | 0.000 | 0.000 |

原因：手写是**手机拍的照片**——纸张阴影、折痕、桌面背景全是暗像素，逐行都能找到长暗带；
而印刷单据是**屏幕截图**，背景纯白，表格线只有 1—2 像素细。
「暗像素连续段」这个特征量到的是拍照光照，不是表格线。

结论：纯 Python 逐像素图像分析在这个场景不可靠，**这条路废弃**，不在代码里留任何痕迹。

### 3.2 第二版：OCR 块特征（采用）

换了个角度：不看图像本身，看**现网 OCR 已经拿到的文字块**——位置、置信度、文字内容。
这些数据本来就在手边，不额外花钱。

跑完 115 张真实样本（13 手写 + 102 印刷）后，逐特征看分离度：

| 特征 | 手写样本区间 | 印刷样本区间 | 分离度 |
| --- | --- | --- | --- |
| 「编码:数量」格式率 | 0.429 — 0.945 | 0.000 — 0.015 | **0.41** |
| 冒号率 | 0.429 — 0.945 | 0.000 — 0.162 | 0.27 |
| OCR 置信均值 | 89.38 — 95.74 | 96.00 — 100.00 | 0.26 |
| 低置信块占比 | 0.182 — 0.476 | 0.000 — 0.111 | 0.07 |
| 块高一致性 | 0.748 — 0.898 | 0.500 — 1.000 | 不可分 |

**「编码:数量」格式率是最强判据**：手写单每一行都是 `1368:10斤`、`1136:2.5斤`，
印刷表格每一格是独立的品类名、独立的数量，几乎不会出现冒号。

OCR 置信度是第二判据：手写体连笔多，通用印刷体 OCR 认不准。

### 3.3 阈值定法

对「格式率」和「置信均值」做二维网格搜索，要求**零错分**，再在其中挑余量最大的一条：

```
判为手写  ⟺  格式率 ≥ 0.20  且  置信均值 < 96.0
```

余量（手写最低 0.429 / 印刷最高 0.015 → 两侧各留 0.2 以上；置信 95.74 / 96.00 → 留 0.26）。
样本少，所以宁可留厚余量也不贴着边界。

**115 张全量验证：准确率 100%，召回 100%，精确 100%。**

## 四、接入点与行为

### 4.1 分流流程

```
拖入图片 → 识别
  ├─ 判别器 detect.判别(OCR块)
  │    ├─ 判为手写 → 手写通道（完整框 + 行列关联 + 候选追踪 + 保守裁决 + 局部复核）
  │    └─ 判为印刷 → 原流程（现网原样，一行未改）
  └─ 手写通道失败 → 只退回**这一张**的原流程，其余图片不受影响
```

判别复用的是现网本来就要做的那一次 `T.tencent_ocr` 调用（有本地缓存），
后续两条通道都命中同一份缓存——**判别不额外产生任何 API 费用**。

### 4.2 模式与界面

`handwriting/modes.py` 新增 `MODE_AUTO`。界面下拉框从三个选项变成四个：

| 选项 | 含义 |
| --- | --- |
| **自动判别**（默认） | 每张图先判是不是手写单据，是就走手写库 |
| 原流程 | 全部走现网流程，行为与升级前完全一致 |
| 手写辅助 | 全部走手写通道 |
| 逐张选择 | 逐张指定，仍用下面两个按钮 |

逐张按钮的优先级高于自动判别——判错了可以手动纠正。

设置项 `手写辅助模式` 的默认值从「关」改为「自动」。

### 4.3 记录契约对齐

手写通道的输出要直接进打印与「待核对」筛选，字段形态必须与现网 `ttsb2.clean_record` 一致，
否则会出现「只有手写通道打出来的标签少个单位」这类单路径问题。

新增 `handwriting.pipeline.规整记录()`：

- 五个字段（`category` / `customer_code` / `weight` / `unit` / `remark`）一律转成去空白的字符串；
  `None` 转空串，不能变成字符串 `'None'`。
- **单位读不出来时兜底「斤」**——对齐现网对手写单的既有规则（手写体上的「斤」被认成怪字很常见，
  不兜底就会印错）。这不是新增策略，是与原流程保持一致。
- 内部标记（`_uncertain` / `_review_reasons` / `_evidence`）原样保留。

### 4.4 降级与安全

- 判别器**任何异常都不抛**，一律退回「不是手写」→ 走原流程。
- 判别器只是**分流器**：两条通道都保留疑点、都标待核对，判错不会导致印错单。
- 手写通道失败只退回**这一张**的原流程，不影响同批其它图片。
- 补丁所有入口仍全部 try/except 包裹，出错退回原行为。

## 六、必须说清的局限

1. **判别器样本偏小**：13 张手写全部来自同一客户（农和），笔迹风格单一。
   换个人的手写单仍需复验。阈值留了厚余量来缓解，但不能当成普适结论。
2. **只能判「像不像手写」，判不了「写得清不清楚」**：写得太潦草的印刷体单据可能被判成印刷——
   这个方向是安全的（走原流程）。
3. **手写通道仍会错**：草写标题（马蹄肉、去皮干葱头）两路都读不准时，保留疑点转人工，
   这是「不能裁决则保留疑点」的正确表现，不是缺陷。
4. **单位仍不作裁决依据**：单位类错误发现不了，这是保守裁决铁律的代价。
5. **待核对比例高**：手写通道会把有疑点的行都标出来，符合方案要求，但核对负担确实增加了。
6. **阶段 5 未做**：暂存构建、实际 EXE 人工验证、数据保护与回退说明仍待进行。
